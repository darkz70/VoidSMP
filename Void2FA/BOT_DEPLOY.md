# Отдельный Python Telegram-бот VoidSMP

**Статус:** исходники и локальные тесты подготовлены. Telegram-аккаунт не создан,
токен не запрашивался, к рабочему Minecraft-серверу никто не подключался.
Старый `release/Void2FA-1.0.0.jar` содержит только встроенный транспорт и **не умеет external**.

## Архитектура для Bothost

```text
Telegram Bot API <--единственный getUpdates--> Python-бот на bothost.ru
                                               |
                         HTTPS-домен Bothost, 0.0.0.0:$PORT
                         POST /v1/sync, HMAC-SHA256 в обе стороны
                                               |
                         Void2FA 1.3.1 bridge (исходящий клиент Paper)
                                               |
                         AuthManager на main thread Paper
                         коды, UUID, привязки, срок, одноразовость
```

Бот хостится отдельно и принимает запросы от плагина. Minecraft-серверу не нужны белый IP,
домен или открытый входящий порт. Бот не принимает Minecraft UUID от пользователя и не объявляет вход разрешённым.
Он передаёт Telegram user/chat ID, текст личного сообщения или callback текущего сообщения.
Плагин проверяет владельца, срок и состояние попытки. `/login` проверяется только плагином.
Тексты остаются в `config.yml` плагина: бот получает уже подготовленный текст.
Исключение — меню команд Telegram: бот публикует его сам (`setMyCommands`) при подключении,
чтобы игроки видели `/help`, `/kick`, `/revoke` и остальные команды в интерфейсе Telegram.

В режиме `external` плагин не вызывает Telegram API, не удаляет webhook и не запускает `getUpdates`.
Если в external оставить непустой `telegram.bot-token`, транспорт не запустится.
В режиме `embedded` сохраняется старый вариант, но его нельзя включать одновременно с сервисом.

## 1. Сборка и тесты без Telegram

Python 3.10+:

```bash
cd Void2FA/bot
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Java 25 и Gradle с поддержкой Java 25 (в CI используется 9.8.2):

```bash
cd Void2FA
gradle build --no-daemon
# build/libs/Void2FA-1.3.1.jar
```

Для Paper API нужен доступ к `repo.papermc.io`. GitHub Actions `.github/workflows/void2fa.yml`
запускает оба набора проверок и сохраняет JAR как артефакт. Не устанавливай старый 1.0.0 для external.

## 2. Создание аккаунта Telegram

Только владелец Telegram создаёт аккаунт: [@BotFather](https://t.me/BotFather) → `/newbot`.
Имя: `VoidSMP | 2FA`; username — свободный, заканчивается на `bot`.
Тексты `/setdescription`, `/setshortdescription`, `/setcommands` сохранены в [BOT_SETUP.md](BOT_SETUP.md).
Не отправляй токен в чат, issue, Git или логи. Webhook не настраивай: сервис использует long polling.

## 3. Общий секрет моста

Секрет моста — **не** токен BotFather. Сгенерируй 32 случайных байта локально:

```bash
python3 -c 'import secrets; print(secrets.token_hex(32))'
```

Сохрани результат в защищённом локальном секрет-хранилище. Один и тот же секрет нужен
плагину и боту. Не используй пример из тестов. Файлы секретов: права `0600`, владелец сервисного пользователя.

## 4. Развёртывание на bothost.ru

Репозиторий подготовлен так, чтобы Bothost мог брать **корень репозитория**: корневые `main.py`
и `requirements.txt` запускают пакет из `Void2FA/bot`. Если загружаешь архив только бота,
используй содержимое `Void2FA/bot` как корень архива: там есть свои `main.py` и `requirements.txt`.

1. Создай бота на Bothost: платформа Telegram, библиотека Python/другая, язык Python.
   В поле Bot Token вставь токен BotFather только в панели Bothost.
2. Подключи Git-репозиторий `https://github.com/darkz70/VoidSMP.git`, ветка `arena/8648743f-voidsmp`,
   или загрузи архив. Главный файл: `main.py` для корня репозитория; `main.py` для архива `Void2FA/bot`.
   После смены главного файла нужен новый деплой, не просто рестарт.
3. Включи опцию домена. Bothost выдаст HTTPS-домен и задаст `PORT`; приложение слушает `0.0.0.0:$PORT`.
   Порт в панели должен совпадать с `PORT`. Без домена плагин не сможет достучаться до бота.
4. В переменных окружения добавь `BRIDGE_SHARED_SECRET` — тот же 64-hex/base64 секрет, что у плагина.
   `BOT_TOKEN`, `DATA_DIR=/app/data`, `PORT`, `DOMAIN` задаёт платформа; `.env` в контейнер не попадает.
   Не добавляй `BOT_TOKEN` в Git. При необходимости используй `BRIDGE_SHARED_SECRET_FILE`, но не оба сразу.
5. Задеплой и открой логи работы. Должно быть сообщение о запуске sync API. Проверь снаружи:
   `https://<домен-бота>/health` должен вернуть JSON `status: ok`.
   `/healthz` станет 200 после готовности Telegram long polling.
6. Скопируй HTTPS-домен бота в конфиг Paper ниже.

Тарифы и лимиты проверь в панели Bothost. На бесплатном тарифе данные могут стираться при перезапуске;
для постоянного SQLite используй тариф с персистентным `DATA_DIR`. Если состояние потеряно,
бот сбросит очереди и заново получит username; старые callback/link/auth ID не станут валидными.
Сервис рассчитан на один экземпляр: не масштабжируй его в несколько процессов с одним токеном/state.

## 5. Установка плагина на тестовую копию Paper

Сначала останови тестовый сервер. Замени старый JAR на собранный `Void2FA-1.3.1.jar`.
Сохрани резервную копию `plugins/Void2FA/config.yml` и `data.yml`.
Новые поля не добавляются автоматически в уже существующий YAML: добавь их вручную.

```yaml
telegram:
  transport: external
  bot-token: ""
  bot-username: ""  # необязательно; после подключения бот сообщит username
  bridge:
    url: "https://<домен-бота-из-панели-Bothost>"
    secret-file: "bridge-secret.txt"
```

Запиши общий секрет в `plugins/Void2FA/bridge-secret.txt`, права `0600`.
Альтернатива для плагина — `VOID2FA_BRIDGE_SECRET` в окружении процесса Paper; она имеет приоритет.
Не публикуй локальный конфиг и не добавляй секрет в Git.

Запусти тестовый Paper. В логе должно быть сообщение о подключении к боту, затем готовность 2FA.
Входящий порт на Minecraft-сервере открывать не нужно. Плагин сам ходит по HTTPS на домен Bothost.
HTTP разрешён только для loopback-тестов (`http://127.0.0.1:8080`), не для интернета.

## 6. Альтернатива: systemd/Docker на своей машине

Если не используешь Bothost, бот всё равно должен быть доступен плагину по HTTPS.
Поставь reverse proxy с TLS перед `0.0.0.0:8080` или используй локальный loopback только для тестов.

Systemd-юнит: `Void2FA/bot/deploy/voidsmp-bot.service`, пример env: `deploy/env.example`.
Docker Compose: `Void2FA/bot/compose.yaml` публикует API только на `127.0.0.1:8080`;
перед ним нужен HTTPS reverse proxy. Не открывай plain HTTP в интернет.

## Частая ошибка запуска на Bothost

Если в логах:

```text
Startup failed: Bridge secret must contain exactly 32 bytes
```

или более новая версия сообщения про `BRIDGE_SHARED_SECRET`, бот нашёл главный файл,
 но не получил корректный **секрет моста**. Это не токен BotFather.

1. Открой настройки бота на Bothost → «Переменные окружения».
2. Добавь переменную с точным именем `BRIDGE_SHARED_SECRET`.
3. Значение: 64 hex-символа, например результат команды ниже, без кавычек и пробелов:

```bash
python3 -c 'import secrets; print(secrets.token_hex(32))'
```

4. Сохрани переменную и сделай перезапуск/новый деплой бота.
5. Тот же самый секрет запиши в Paper: `plugins/Void2FA/bridge-secret.txt`
   или в `VOID2FA_BRIDGE_SECRET` окружения процесса Paper.

Не используй `BOT_TOKEN` как `BRIDGE_SHARED_SECRET` и не публикуй секрет в чате/Git.
Если секции переменных окружения нет на текущем тарифе Bothost, нужен тариф с этой возможностью
или отдельный секрет-файл, доступный процессу бота; не хардкодь секрет в репозитории.

## 7. Проверка сценариев

1. В игре `/2fa link`; отправь боту `/link КОД` или открой ссылку `/start LINK_КОД`.
2. `/status` показывает привязку; повторная привязка тем же аккаунтом не создаёт вторую запись.
3. Повторный вход: получен код и кнопки. Верный `/login КОД` подтверждает, неверный — нет.
4. «Отклонить» завершает попытку; старая кнопка не подтверждает следующий вход.
5. Выход игрока и таймаут отменяют попытку. `/2fa resend` выдаёт новый auth ID; старая кнопка не работает.
6. `/unlink` работает только вне незавершённого входа. Команды в группе игнорируются.
7. Останови бота: новые входы ведут себя согласно `lockdown-if-unavailable`.
   **Текущее значение false означает fail-open для новых входов, включая привязанных игроков.**
   После тестов выбери осознанную политику; для строгой защиты установи true и настрой отдельный
   аварийный доступ администратора. Уже ожидающие попытки не разрешаются автоматически.
8. Перезапусти бота: SQLite в `DATA_DIR` сохраняет Telegram offset и очереди. Перезапусти Paper:
   меняется instance ID, старые callback/link/auth ID больше не действуют.
9. После подтверждения входа зайди с того же IP: код не требуется. С другого IP — требуется.
10. `/lock` в Telegram кикает онлайн-игрока и не пускает никого до `/unlock`; `/devices` и `/untrust` управляют доверенными IP.
11. `/kick` завершает текущий вход и сбрасывает короткую сессию, но сохраняет доверенные устройства.
12. `/revoke` (или `/untrust all`) удаляет все доверенные устройства, сбрасывает сессию и кикает онлайн-игрока.
13. `/help` и `/start` показывают все команды, а в меню Telegram рядом с полем ввода видны команды бота.
    Команды работают только в личном чате привязанного владельца. Python-бот только передаёт текст; обработка остаётся в плагине.

Административное восстановление: `/2faadmin reset НИК` с `void2fa.admin`.
Блокировка: `/2faadmin lock НИК`, разблокировка: `/2faadmin unlock НИК`.
Не выдавай `void2fa.bypass` обычным игрокам: оно полностью пропускает 2FA, но не обходит блокировку аккаунта.

## Протокол и ограничения

Подробности: [BRIDGE_PROTOCOL.md](BRIDGE_PROTOCOL.md). Доставка команд — at-least-once через durable
Telegram offset и idempotency key плагина; доставка сообщений — at-least-once через SQLite event IDs.
Между успешной отправкой в Telegram и записью SQLite возможен повтор сообщения при аварийном рестарте.
Это не повторная авторизация: решение и одноразовость остаются в плагине. SQLite хранит offset,
очереди, event IDs и ссылки на сообщения, но не код входа и не токен. Telegram сам хранит отправленный код в чате.

Сервис рассчитан на **один экземпляр на токен и один Minecraft-сервер на секрет/bridge**.
Файл-замок защищает один state-каталог; Telegram 409 останавливает конкурирующий процесс.
Не запускай embedded и external с одним токеном. Смена бота требует отдельного чистого state-каталога.
